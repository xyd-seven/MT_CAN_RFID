# 代码审查报告与一次性修改方案

生成时间：2026-06-26
审查范围：当前工作区中测试执行、用例自动化、OTA 异常注入相关修改。

## 结论

当前代码已能编译通过，新增的“当前用例日志清空”和 OTA 注入项主流程基本可用。但走读后发现 4 个建议修复点，其中 3 个会影响自动判定可信度或历史会话兼容性，建议一次性修复后再继续实测。

## 代码审查发现

### P1：历史证据日志中的接收方向可能无法被自动判定识别

位置：

- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:93`
- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:121`
- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:141`

问题：

`isReceiveFrame()` 当前只识别正常 UTF-8 的“接收”。但项目历史代码和历史会话日志中曾出现过乱码方向文本，例如旧逻辑里使用过 `鎺ユ敹`。如果打开历史会话后执行自动判定，旧证据中的接收帧会被过滤掉，导致“响应缺失 / 证据不足 / 阻塞”等误判。

影响：

- 打开历史会话后复判风险较高。
- 用户已明确提过“不能打开历史会话”的使用场景，历史证据兼容应优先保证。

建议：

增强方向识别函数，兼容：

- `接收`
- `Rx`
- `RX`
- 旧乱码文本 `鎺ユ敹`
- 必要时兼容包含“接收”或“收”的历史显示文本

同时建议增加 `isTransmitFrame()`，避免后续再以字符串散落判断。

### P1：NVM 写入回读判定未限定“写入响应之后”的广播证据

位置：

- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:1042`
- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:1111`
- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:1124`

问题：

`mt.nvm_device_id_writeback_verify` 和 `mt.nvm_sn_reboot_verify` 最终调用 `judgeDeviceIdPrefix()`，该函数只要在整个证据窗口内找到 0x2C4/0x2C5 且前缀匹配，就会通过。它没有确认这些广播帧是否出现在 0x2E 写入肯定响应之后，也没有确认 NVM-006 的重启后回读。

影响：

- 如果用例开始后、写入响应前已经采集到设备 ID 广播，则可能被当作写入后的回读证据。
- NVM-006 “写 SN 后重启验证”可能未真正验证重启后的保持性。

建议：

新增按时间窗口判定的辅助函数：

- 找到 0x2E 写入肯定响应 `03 6E E7 xx` 的时间。
- 对 NVM-002：仅统计该时间之后的 0x2C4/0x2C5。
- 对 NVM-006：找到重启请求/响应后，仅统计重启之后的 0x2C4/0x2C5。
- 若时间戳无效，则降级为阻塞，而不是直接通过。

### P2：连续 NVM 写入用例响应判定过宽，可能被无关响应误判通过

位置：

- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:1136`
- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp:1150`

问题：

`judgeNvmBusyOrSerializedWrite()` 在已采集两次写入请求后，只要存在任意 0x107 且首字节为 `03` 的响应帧，就可能判定通过。`03` 只是单帧长度，不代表一定是 `0x2E` 写入响应。

影响：

- 可能被其它诊断服务的 3 字节响应误触发通过。
- 连续写入忙处理/串行处理的证据不足够严格。

建议：

将通过条件收紧为以下之一：

- 存在 `03 6E E7 xx` 写入肯定响应。
- 存在 `03 7F 2E NRC` 否定响应，且 NRC 在允许范围内，例如 `21/22/78/31/13`。
- 如果只有请求没有响应，判定为阻塞。

同时在结果说明中明确是“设备串行接受”还是“设备忙/拒绝第二次写入”。

### P2：用例 JSON 被整体重排，增加后续合并和审查成本

位置：

- `F:\TestTools\MT_CAN\CAN_RFID_Qt\resources\testcases\meituan_rfid_can_testcases.json`

问题：

当前 JSON 文件被 PowerShell `ConvertTo-Json` 整体重写，字段顺序、缩进和部分字符转义发生大范围变化。功能上通常可用，但会带来：

- diff 过大，难以审查真实业务变更。
- 后续与 qingju/dev 分支合并冲突概率升高。
- 一些文本被转义为 `\u003e`，人工阅读体验下降。

建议：

用 Python 按原始 UTF-8 格式重新写入 JSON，并尽量保留字段顺序。若无法完全恢复原格式，至少使用稳定格式：

- `ensure_ascii=False`
- `indent=4`
- 保持对象字段顺序
- 文件末尾补换行

后续修改用例 JSON 时，避免使用 PowerShell `ConvertTo-Json` 直接写回全文件。

## 一次性修改方案

### 目标

一次性完成以下修复：

1. 兼容历史证据方向文本，保证历史会话复判可用。
2. 收紧 NVM 写入/回读判定时间窗口，避免用写入前广播误判通过。
3. 收紧连续 NVM 写入响应判定，避免无关 0x107 响应误判。
4. 规范化用例 JSON 文件格式，降低后续合并风险。

### 修改文件

- `F:\TestTools\MT_CAN\CAN_RFID_Qt\application\testcasejudge.cpp`
- `F:\TestTools\MT_CAN\CAN_RFID_Qt\resources\testcases\meituan_rfid_can_testcases.json`

如实现过程中发现需要复用已有工具函数，可小范围补充同文件内私有 helper，不新增跨模块依赖。

### 具体实现步骤

#### 1. 修复接收方向兼容

在 `testcasejudge.cpp` 中调整：

```cpp
bool isReceiveFrame(const EvidenceFrame &frame)
{
    const QString direction = frame.direction.trimmed();
    return direction == QStringLiteral("接收") ||
           direction.compare(QStringLiteral("RX"), Qt::CaseInsensitive) == 0 ||
           direction == QStringLiteral("鎺ユ敹") ||
           direction.contains(QStringLiteral("接收"));
}
```

可选增加：

```cpp
bool isTransmitFrame(const EvidenceFrame &frame)
```

仅在后续确实需要区分发送帧时使用。

#### 2. 增加响应时间点查找 helper

新增 helper：

```cpp
bool findFirstFrameData(...);
QVector<EvidenceFrame> framesAfter(...);
```

项目中已有类似函数，优先复用，缺失时只在匿名命名空间内补充。

新增更明确的工具：

```cpp
bool findWritePositiveResponse(const QVector<EvidenceFrame> &frames,
                               const QString &didLowByte,
                               EvidenceFrame *matched);

QVector<EvidenceFrame> receiveFramesAfter(const QVector<EvidenceFrame> &frames,
                                          const QDateTime &baseTime,
                                          const QList<int> &ids,
                                          int graceMs = 0);
```

#### 3. 收紧 NVM 设备 ID / SN 回读判定

调整 `judgeNvmWriteAndVerify()`：

- 对 `mt.nvm_device_id_writeback_verify`：
  - 必须先找到 `03 6E E7 E1`。
  - 只使用该响应之后的 0x2C4/0x2C5 做 `requiredPrefix` 和空值判定。

- 对 `mt.nvm_sn_reboot_verify`：
  - 必须先找到 `03 6E E7 E1`。
  - 必须找到重启请求 `01 02` 或重启响应 `01 42`。
  - 只使用重启响应之后的 0x2C4/0x2C5 做判定。
  - 如果没有重启响应但有重启请求，判定阻塞并提示“缺少重启后广播证据”。

- 对 `mt.nvm_write_same_value_and_verify`：
  - 必须找到 `03 6E E7 E0`。
  - 只使用该响应之后的 0x2C3 作为回读证据。

#### 4. 收紧连续写入响应判定

调整 `judgeNvmBusyOrSerializedWrite()`：

- 保留“两次 0x2E E7xx 请求”的前置条件。
- 移除“任意 0x107 首字节 03 即通过”的条件。
- 新通过条件：
  - 至少一个 `03 6E E7 xx`
  - 或至少一个 `03 7F 2E NRC`
- 如果出现否定响应但 NRC 不在允许列表，判定失败。
- 如果无响应，判定阻塞。

推荐允许 NRC：

```text
21, 22, 31, 78, 13
```

#### 5. 规范化 JSON

用 Python 读取并写回：

```python
json.dump(cases, file, ensure_ascii=False, indent=4)
file.write("\n")
```

要求：

- 不改变用例内容。
- 不用 PowerShell `ConvertTo-Json`。
- 写回后抽查以下用例字段仍在：
  - `MT-RFID-COM-002`
  - `MT-RFID-COM-004`
  - `MT-RFID-CTRL-002`
  - `MT-RFID-NVM-001`
  - `MT-RFID-NVM-002`
  - `MT-RFID-NVM-003`
  - `MT-RFID-NVM-006`
  - `MT-RFID-OTA-001`

## 风险说明

- NVM 判定收紧后，部分之前“通过”的用例可能变为“阻塞”。这是预期结果，因为新逻辑要求更可靠的回读证据。
- JSON 格式化会再次改变文件 diff，但这是一次性治理；后续应保持稳定写法。
- 历史乱码方向兼容只用于判定层，不影响新日志生成格式。
