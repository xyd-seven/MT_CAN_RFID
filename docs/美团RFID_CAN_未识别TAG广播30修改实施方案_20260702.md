# 美团 RFID CAN 未识别 TAG 广播 0x30 修改实施方案

## 1. 背景

客户最新要求：终端在未识别 TAG 的情况下，TAG 广播帧内容不再使用 `0x00`，而是使用 `0x30`。

本次变更主要影响 TAG 分片广播帧：

- `0x2C1`：TAG 前 8 字节
- `0x2C2`：TAG 后 8 字节
- `0x2C6`：超高频 TAG 扩展 8 字节

`0x2C0` 的卡状态定义不应混淆处理：未识别 TAG 仍以 `Byte2=0x00` 表示。也就是说，本次变更不是把 `0x2C0 Byte2` 从 `0x00` 改为 `0x30`，而是把未识别 TAG 时的 TAG 分片占位内容从全 `0x00` 调整为全 `0x30`。

## 2. 检查结论

当前代码中存在以下受影响点：

| 功能范围 | 当前风险 | 是否需要修改 |
|---|---|---|
| RFID 监控 | `0x2C1/0x2C2/0x2C6` 收到全 `0x30` 时会被解析成字符串 `00000000`，可能拼成 `0000000000000000` 并显示为当前 TAG | 需要 |
| 压力测试 | TAG 内容校验仅检查 16/24 位十六进制字符，全 `0` 字符串会被误判为有效 TAG，影响成功率、TAG 有效率、不同 TAG 统计 | 需要 |
| 产线检测 | 主要依赖 `0x2C0 Byte2` 判断有无 TAG，逻辑受影响较小；但当前 TAG 展示可能被 RFID 监控状态中的占位 TAG 污染 | 建议修正 |
| 测试执行 | `MT-RFID-BC-006`、`MT-RFID-ERR-004` 等无 TAG/旧 TAG 清除类用例仍按“全 0”判定，会与新终端逻辑冲突 | 需要 |
| 测试用例资源 | 用例预期结果中仍有“广播值为 00”“广播00”等旧描述 | 需要 |
| CAN 原始日志 | 原始帧记录应保持真实帧数据，不应把 `0x30` 改写成空值 | 不修改 |
| OTA、诊断、NVM | 与 TAG 未识别占位值无直接关系 | 不修改 |

## 3. 修改原则

1. 保持 `0x2C0 Byte2=0x00` 作为“未识别 TAG”的状态判定依据。
2. TAG 分片帧中全 `0x30` 仅作为“未识别 TAG 占位值”，不能作为有效 TAG 参与统计或产线判定。
3. 原始日志、证据日志中的原始 CAN Data 必须保持真实记录，不做替换。
4. 解析显示、统计判定、测试执行判定统一调用公共判断函数，避免各模块分别硬编码。
5. 不保留全 `0x00` 兼容判定。未识别 TAG 分片必须按客户最新要求判定为全 `0x30`，历史全 `0x00` 证据仅作为旧版本资料，不作为当前用例通过依据。

## 4. 具体修改方案

### 4.1 协议公共能力

修改文件：

- `CAN_RFID_Qt/rfidprotocol.h`
- `CAN_RFID_Qt/rfidprotocol.cpp`

新增公共方法：

```cpp
static bool isUnrecognizedTagPlaceholderPayload(const QByteArray &payload);
static bool isUnrecognizedTagPlaceholderText(const QString &text);
```

建议规则：

- `isUnrecognizedTagPlaceholderPayload`：经典 CAN DLC 为 8，且 8 个字节全部为 `0x30` 时返回 `true`。
- `isUnrecognizedTagPlaceholderText`：字符串长度为 8、16 或 24，且全部字符为 `'0'` 时返回 `true`。

注意：`isUnrecognizedTagPlaceholderText` 不能单独作为卡状态依据，只能用于 TAG 内容过滤。是否“未识别 TAG”仍以 `0x2C0 Byte2=0x00` 为准。

### 4.2 RFID 监控

修改文件：

- `CAN_RFID_Qt/application/rfidservice.cpp`
- 必要时同步 `CAN_RFID_Qt/application/rfidservice.h`

修改点：

1. 处理 `0x2C1/0x2C2/0x2C6` 时，若帧数据为全 `0x30`，对应 TAG 分片不作为有效 TAG 内容。
2. `updateTagText()` 拼接 TAG 时，如果拼接结果为全 `0` 占位字符串，则 `currentState.tag` 应保持为空。
3. 当 `0x2C0 Byte2=0x00` 时继续清空当前 TAG，避免旧 TAG 残留。
4. 展示层保持“未识别”，不要显示 `0000000000000000`。

预期效果：

- RFID 监控界面不会把未识别占位值显示成有效 TAG。
- 解析日志仍保留原始 Data，例如 `30 30 30 30 30 30 30 30`。

### 4.3 压力测试

修改文件：

- `CAN_RFID_Qt/application/stresstestservice.cpp`
- 必要时同步 `CAN_RFID_Qt/application/stresstestservice.h`

修改点：

1. `updateTagPart()` 收到全 `0x30` 分片时，不更新为有效 TAG 分片，或更新后在 `currentTagText()` 中过滤为无效占位。
2. `currentTagIsValid()` 和 `isValidTagText()` 增加占位 TAG 排除逻辑：全 `0` 的 16/24 位字符串不能判定为有效 TAG。
3. 当 `0x2C0 Byte2=0x00` 时继续计入“未识别”，并清空当前 TAG。
4. CSV 样本中建议保留原始状态结果，但 `current_tag` 不写入占位 TAG，避免后续统计误读。

预期效果：

- 未识别时不会增加有效 TAG 数。
- 不会把占位值计入“不同 TAG”。
- TAG 有效率、成功率、连续失败统计不被全 `0x30` 广播污染。

### 4.4 产线检测

修改文件：

- `CAN_RFID_Qt/application/productiontestservice.cpp`
- 可能涉及 `CAN_RFID_Qt/mainwindow.cpp` 的展示刷新逻辑

检查结论：

- 产线检测当前主要通过 `RfidState.cardStatus` 判断是否识别到 TAG，逻辑基础仍正确。
- 风险点在于 `RfidState.tag` 可能被 RFID 监控解析成 `0000000000000000` 后展示或用于成功记录。

修改点：

1. 在 RFID 监控层过滤占位 TAG 后，产线检测可自然获得空 TAG。
2. 为增强容错，`recordSuccess()` 或进入成功统计前可增加一层保护：如果 TAG 字符串为全 `0` 占位值，则不计成功，记录为“未识别 TAG 占位值，不作为有效读卡结果”。

预期效果：

- 产线检测不会因占位 TAG 误判通过。
- 对现有正常 TAG、SN 写入、硬件版本写入流程无影响。

### 4.5 测试执行判定

修改文件：

- `CAN_RFID_Qt/application/testcasejudge.cpp`

受影响模板：

- `mt.semi.tag_absent_cleared`
- `mt.semi.tag_residue_cleared`
- 其他直接检查 TAG 分片全 `0` 的辅助函数

修改点：

1. 将 `hasAllZeroFrame()` 调整为更明确的公共判定，例如：

```cpp
hasUnrecognizedTagPlaceholderFrame(frames, canId)
```

2. 新判定只接受 8 字节全部为 `0x30` 的 TAG 分片占位值；全 `0x00` 不再作为通过条件。

3. 判定通过文案调整为：

```text
已采集到无 TAG 状态，且 TAG 分片为未识别占位值 0x30。
```

4. 若采集到非占位值，则失败文案调整为：

```text
无 TAG 状态下 TAG 分片不是 0x30 占位值，可能仍保留旧 TAG 或存在异常广播。
```

注意：

- `MT-RFID-BC-002`、`MT-RFID-BC-004`、`MT-RFID-CTRL-004` 等只检查 `0x2C0 Byte2=0x00` 的用例，不需要改为 `0x30`。
- `CTRL-005` 中开始/停止检测后检查 `Byte2=0x00` 的逻辑不应修改。

### 4.6 测试用例资源

修改文件：

- `CAN_RFID_Qt/resources/testcases/meituan_rfid_can_testcases.json`

需要更新的用例描述：

| 用例 ID | 当前问题 | 修改建议 |
|---|---|---|
| `MT-RFID-BC-006` | 预期结果仍写“广播值为00” | 改为“未识别到 TAG 时 0x2C1/0x2C2 广播值为 0x30，不应保留上一次 TAG” |
| `MT-RFID-ERR-004` | basis 和 expectedResult 仍写“未识别TAG广播00” | 改为“未识别 TAG 广播 0x30；0x2C1/0x2C2/0x2C6 不保留旧 TAG” |
| 其他无 TAG 相关用例 | 若只描述 `0x2C0 Byte2=0x00`，不修改 | 避免误把状态字节改成 `0x30` |

### 4.7 证据日志与报告

修改文件：

- `CAN_RFID_Qt/application/testcaseservice.cpp`
- 如有必要，调整证据摘要文字

建议：

1. 原始帧记录保持真实帧数据。
2. 关键帧和判定结论中增加解释：

```text
0x2C1/0x2C2 为 30 30 30 30 30 30 30 30，按新协议判定为未识别 TAG 占位值。
```

3. 不建议在证据日志中过度展开每一帧，只需在判定结论中说明占位值含义。

## 5. 建议执行步骤

### 第一批：公共解析与业务保护

1. 在 `RfidProtocol` 增加未识别 TAG 占位值判断函数。
2. 修改 `RfidService`，避免 RFID 监控显示占位 TAG。
3. 修改 `StressTestService`，避免压力测试把占位 TAG 计为有效 TAG。
4. 修改 `ProductionTestService` 成功判定保护，防止占位 TAG 被计入产线成功样本。

### 第二批：测试执行与用例资源

1. 修改 `TestCaseJudge` 无 TAG 分片判定，严格按 `0x30` 占位值判定，不兼容旧全 `0x00` 历史数据。
2. 更新 `meituan_rfid_can_testcases.json` 中涉及“广播00”的用例描述。
3. 调整证据日志判定说明，明确 `0x30` 是未识别占位值。

### 第三批：验证

1. 编译 release 版本。
2. 使用无 TAG 场景验证 RFID 监控：
   - `0x2C0 Byte2=0x00`
   - `0x2C1/0x2C2/0x2C6` Data 为全 `30`
   - 当前 TAG 显示为空或未识别，不显示 `0000000000000000`
3. 执行压力测试短样本：
   - 无 TAG 时计入未识别，不计入有效 TAG
   - 有 TAG 时仍可正确统计成功和 TAG 有效率
4. 执行产线读卡流程：
   - 无 TAG 不通过
   - 有有效 TAG 正常通过
5. 执行测试用例：
   - `MT-RFID-BC-006`
   - `MT-RFID-ERR-004`
   - 与 `0x2C0 Byte2=0x00` 相关的 `BC-002`、`BC-004`、`CTRL-004`、`CTRL-005`

## 6. 风险与容错

| 风险 | 处理方式 |
|---|---|
| 真实 TAG 可能出现全 `0` 字符串 | 仅在 `0x2C0 Byte2=0x00` 或全分片占位场景下按未识别处理；正常识别状态仍需结合状态字节判断 |
| 旧样机仍广播全 `0x00` | 按客户最新需求判定为不符合当前用例预期；如需追溯旧样机，仅在报告备注中说明历史协议差异 |
| 压力测试历史 CSV 统计口径变化 | 新 CSV 不再把占位 TAG 写成有效 TAG，历史数据不回改 |
| 修改影响其他协议 | 修改限定在美团 RFID CAN 解析和测试执行逻辑，不触碰青桔、RS485、OTA、NVM 主流程 |

## 7. 结论

本次变更建议按两批代码修改完成：第一批处理公共解析、RFID 监控、压力测试、产线检测；第二批处理测试执行判定、用例资源和证据说明。

优先级最高的是 RFID 监控和压力测试，因为当前全 `0x30` 会被解析成 `0000000000000000`，容易被误认为有效 TAG。测试执行中无 TAG 清除类用例也必须同步调整，否则新终端会按客户要求广播 `0x30`，但上位机仍按全 `0x00` 判定失败。
